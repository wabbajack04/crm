# СтройКонтур

Мини-CRM строительной компании на React, TypeScript и Supabase. Постановщик создаёт объекты и назначает задачи, исполнитель выполняет их, а автор проверяет результат.

## Запуск

1. Создайте проект Supabase. В настройках Authentication отключите регистрацию новых пользователей и анонимный вход. Оставьте вход по email и паролю. Эти ограничения уже заданы в локальной конфигурации. [Настройки Supabase Auth](https://supabase.com/docs/guides/auth/general-configuration)
2. Выполните [миграцию](supabase/migrations/202611040001_crm.sql) в SQL Editor проекта или примените её через Supabase CLI командой `supabase db push` после привязки проекта.
3. В Authentication → Users вручную создайте три подтверждённые учётные записи. Используйте уникальные пароли и передайте их проверяющим отдельно.

   | Email | Роль |
   | --- | --- |
   | manager@crm.example.com | Постановщик |
   | worker1@crm.example.com | Исполнитель |
   | worker2@crm.example.com | Исполнитель |

4. Выполните [demo.sql](supabase/demo.sql) один раз в SQL Editor. Он создаст профили, три объекта и пять задач во всех предусмотренных статусах. Если использовали другие email, замените их в начале скрипта.
5. Скопируйте `.env.example` в `.env.local`. Укажите URL проекта и его **Publishable key**. Для старых проектов подойдёт публичный ключ `anon`.
6. С Node.js 22.12+ выполните `npm ci` и `npm run dev`. Откройте адрес, указанный в терминале.

Для размещения на Vercel импортируйте репозиторий и выберите Vite. Укажите обе переменные из `.env.example`. Команда сборки — `npm run build`, папка результата — `dist`. Навигация использует фрагмент URL, поэтому правила перенаправления не нужны. Добавьте домен приложения в Authentication → URL Configuration. Для GitHub достаточно отправить исходники из этой папки, включая миграции и lock-файл.

## Правила доступа

Права на чтение и изменение строк проверяет Supabase через политики RLS. Исполнитель видит назначенные ему задачи, их историю и объекты, в которых эти задачи находятся. Постановщики видят все объекты и задачи. Автор может менять поля своей задачи до начала работы, удалить её, принять результат или вернуть его на доработку.

Исполнитель начинает новую или возвращённую задачу и отправляет её на проверку. Изменить статус можно только через функцию `transition_task`. База блокирует строку на время операции, проверяет участника и допустимость перехода, а для возврата требует комментарий. Статус и запись истории сохраняются одной транзакцией. Автор, статус и время создания новой задачи устанавливаются базой. Клиентам разрешено только читать историю видимых задач. В клиенте используется только публичный ключ.

## Как проверить

- Под первым исполнителем откройте «Мои задачи» и ЖК Северный. Задача «Принять арматуру» и объект «Склад Восточный» должны быть скрыты. Под вторым исполнителем они доступны.
- Под первым исполнителем возьмите «Проверить ограждение площадки» в работу и отправьте на проверку. Под постановщиком верните с комментарием. Повторите цикл и примите задачу. Сверьте историю под обеими ролями.
- Через Supabase API с токеном исполнителя попробуйте прочитать чужую задачу и историю. Ожидаются пустые результаты. Попробуйте изменить статус прямым `PATCH`, записать историю и вызвать запрещённый переход через `rpc/transition_task`. Ожидается отказ.
- Для проверки границы между постановщиками добавьте вторую учётную запись и профиль с ролью `manager`. Чужая задача видна, но отдельное редактирование, удаление и проверка недоступны.
- Проверьте каскадное удаление на отдельном объекте. После удаления объекта его задачи и записи истории исчезают.

## Принятые решения

- Правило «только по своим задачам» применено к проверке, редактированию и отдельному удалению задач. По ТЗ любой постановщик управляет объектами. Удаление объекта каскадно удаляет все его задачи, включая задачи других авторов. Интерфейс предупреждает об этом перед удалением.
- Автор может отдельно удалить свою задачу в любом статусе. Ограничение «до начала работы» применяется к редактированию. Возврат на доработку позволяет исполнителю снова взять задачу в работу.
- Создание задачи сохраняется как первое событие истории. Имя и роль профиля назначает администратор, а назначить задачу можно только пользователю с ролью исполнителя.
